# Spec: Cross-repo skill source of truth (marketplace → chowa)

Status: **Draft** — awaiting explicit approval before Stage 2 (implementation plan).

## Problem Statement

`franprince/skills-marketplace`'s `chowa-skill` plugin was hand-adapted from
this repo's own canonical skill (`plugins/chowa/skills/chowa/SKILL.md`):
same spec → plan → execute pipeline, branching rules, commit conventions,
PR-mergeability check — with every `chowa <command>` replaced by native
tool-call instructions, and CLI-only capabilities (live model routing,
quota-aware session auto-resume) explicitly scoped out.

That adaptation was a one-time copy, not a standing relationship — and it
already drifted within the same session it was created in. Right after
`chowa-skill` shipped, this repo's own three skill files (canonical,
self-hosted, portable) gained a new shared-workflow rule (the PR closing-line
convention) that never made it back into `chowa-skill`. Nothing caught
that, because nothing connects the two repos: any future edit to shared
workflow content in one place requires a human to remember to hand-port it
to the other, with no mechanism enforcing it and no visibility into when it
falls out of sync.

The user has decided to resolve this by inverting the relationship:
`skills-marketplace`'s `chowa-skill` becomes the canonical source for
*shared* workflow content — the parts that apply regardless of whether a
CLI/bundled engine exists underneath. This repo's three skill files should
be generated from it, with chowa's own CLI-specific material (the
`chowa <command>` invocation layer, live model routing via `chowa route`,
quota-aware session auto-resume, the Claude Code Bridge) layered on top
rather than duplicated by hand.

## Goals

- **G1.** Designate `skills-marketplace/plugins/chowa-skill/skills/chowa-skill/SKILL.md`
  as the single authored copy of every workflow rule shared between the two
  projects (spec → plan → execute pipeline, branching/PR workflow including
  the mergeability check and the closing-line sign-off, commit conventions,
  code quality verification, delegation philosophy).
- **G2.** This repo's canonical skill (`plugins/chowa/skills/chowa/SKILL.md`)
  is generated by combining that shared content with chowa-specific overlay
  content that only makes sense where a CLI/bundled engine exists (the
  invocation table, `chowa route`/model routing, session auto-resume,
  Claude Code Bridge, mechanical delegation via `chowa-mechanical`).
- **G3.** The self-hosted (`.claude/skills/chowa/SKILL.md`) and portable
  (`.agents/skills/chowa/SKILL.md`) copies continue to derive from the
  canonical one exactly as they do today (`scripts/sync-skill.ts`) — this
  spec adds a layer *before* that step, not a replacement for it.
- **G4.** Drift is either impossible or loudly detected: a CI check (or
  the existing `check:skill` step, extended) fails if chowa's generated
  skill content no longer matches what the marketplace's shared content
  would currently produce.
- **G5.** Reconcile the content that has *already* diverged (the PR
  closing-line convention chowa has and `chowa-skill` doesn't; any other
  differences a careful diff turns up) as part of this change, not as a
  follow-up.

## Non-Goals

- **Not rewriting `chowa-skill`'s scoped-out sections back in.** Live model
  routing and session auto-resume stay chowa-only overlay content, not
  shared content pulled into the marketplace skill.
- **Not merging the two repos.** They stay separate git repositories with
  separate release cadences; this is about one specific content
  relationship between them, not a monorepo migration.
- **Not solving generic cross-repo package distribution.** This is scoped
  to skill markdown content specifically, not a general "chowa the CLI
  depends on a published chowa-skill package" mechanism.

## Key Open Question: the sync mechanism

This is the crux design decision and needs to be resolved before Stage 2,
since it drives what "generated from" concretely means.

**Option A — Git submodule.** Add `skills-marketplace` (or a narrower
subtree) as a submodule in this repo, read the shared file from the
checked-out path. Fully offline once checked out; pinned to an exact
commit by construction, so drift can't happen silently. Cost: submodules
are a well-known contributor-experience papercut (`--recurse-submodules`
or a follow-up `git submodule update --init` is easy to forget), and every
shared-content change now requires a second commit in *this* repo (the
submodule pointer bump) beyond the one in `skills-marketplace`.

**Option B — Fetch at sync time, pinned to a commit SHA.** `sync-skill.ts`
fetches the shared file from
`https://raw.githubusercontent.com/franprince/skills-marketplace/<pinned-sha>/plugins/chowa-skill/skills/chowa-skill/SKILL.md`,
applies chowa's overlay on top, writes the local files as it does today.
Pinning to a SHA (not `main`) keeps CI deterministic — an unrelated
marketplace commit landing mid-PR can't flip this repo's `check:skill`
result. Bumping the pin is a one-line constant change. Cost: introduces a
network dependency into a build/CI step that has never had one before in
this project — worth flagging explicitly as a first, since it sets a
precedent, and CI needs a clear, actionable failure message if the fetch
itself fails (rate limit, network blip, repo renamed) rather than
misreporting that as "content drifted."

**Option C — No mechanical sync; disciplined manual propagation.**
Document the relationship in both repos' skill files (already partly true)
and rely on whoever edits shared content in one place to port it to the
other, same as today. Cheapest, but is exactly the failure mode G4/G5
exist to fix — this project has repeatedly preferred mechanical
enforcement over prose discipline elsewhere (the push-guard hook exists
for exactly this reason), so falling back to prose here would be a
regression relative to how the rest of this repo is built.

**Recommendation:** Option B. It avoids the submodule onboarding tax,
keeps CI deterministic via the pin, and matches this repo's existing
preference for mechanical checks over documented discipline — at the
acknowledged cost of a new kind of dependency (network I/O in `check:skill`)
that this spec should call out plainly rather than bury.

## Affected Interfaces

- `scripts/sync-skill.ts` — gains a fetch-and-overlay step ahead of its
  existing region-swap logic; `REGION_SWAPS` likely needs to become
  "shared content + chowa overlay regions" rather than purely
  "canonical → portable" swaps.
- `.github/workflows/ci.yml` — `check:skill`'s job needs network access
  (already implicit for `actions/checkout`, but this is a new outbound
  call to a different host) and a clear failure message distinguishing
  "fetch failed" from "content drifted."
- `plugins/chowa/skills/chowa/SKILL.md`, `.claude/skills/chowa/SKILL.md`,
  `.agents/skills/chowa/SKILL.md` — all three become at least partially
  generated rather than hand-edited; whichever sections come from the
  shared source need to stop being edited by hand in this repo, or a hand
  edit here will get silently clobbered on the next sync.
- `franprince/skills-marketplace`'s `chowa-skill` — becomes something
  edited with this repo in mind, not a one-off snapshot; may need its own
  documentation note that it's now a dependency other projects sync
  against, not just a standalone plugin.

## Edge Cases

- **A shared-content edit lands in `skills-marketplace` with no
  corresponding pin bump here.** This repo's generated skill silently
  keeps using the old content until the pin is bumped — is that
  acceptable (explicit, deliberate versioning) or does it need its own
  staleness check (e.g., `check:skill` warns if the pin is more than N
  days behind the marketplace's current `main`)?
- **The overlay mechanism needs to insert CLI-specific content *inside* a
  section that's otherwise shared** (e.g., "PR Description Generation" is
  shared prose plus a chowa-only `chowa pr --base <branch>` code block
  inserted mid-section) — the existing marked-region convention
  (`<!-- chowa:x:start/end -->`) was designed for "strip this whole
  region," not "splice chowa-only content into a shared paragraph." This
  may need a second marker type (an insertion point rather than a
  replaceable region).
- **`chowa-skill` itself has content chowa's overlay shouldn't duplicate**
  (its own "What this skill intentionally does not do" section, written
  from the pure-skill's point of view) — the overlay step needs to know
  which parts of the shared file to skip, not just what to add.
- **Network failure during a release build.** If Option B is chosen,
  what's the behavior when `plugins/chowa/dist/` needs rebuilding on a
  `release/*` branch and the fetch fails — hard failure (correct, but
  blocks a release on marketplace-repo availability) or fall back to a
  last-known-good cached copy committed alongside the pin?

## Acceptance Criteria

- [ ] Every rule currently duplicated by hand across `chowa`'s three skill
      files and `chowa-skill` exists in exactly one authored place
      (`skills-marketplace`), not three.
- [ ] The already-diverged PR closing-line convention is reconciled:
      `chowa-skill` gains it (from the shared source), and chowa's own
      copies keep it without a second hand-authored copy of the prose.
- [ ] `bun run sync:skill` (or its successor) regenerates all three of
      chowa's skill files from the pinned shared source plus chowa's own
      overlay content, byte-for-byte reproducibly given the same pin.
- [ ] `bun run check:skill` (or its successor) fails clearly and
      specifically when: (a) the generated content doesn't match what's
      committed, or (b) the shared source can't be fetched — distinct
      failure messages for each.
- [ ] CI's `check:skill` job passes on a clean `develop` with no
      network-flakiness-driven false failures across several runs.
- [ ] Chowa-only content (model routing, session auto-resume, Claude Code
      Bridge, mechanical delegation) is never lost or duplicated into
      `chowa-skill`.
- [ ] `chowa-skill`'s own intentionally-scoped-out section is preserved
      and not clobbered by the overlay mechanism.
